문제 상황

초기에는 기획과 디자인에 맞춰 여러 화면을 빠르게 구현하는 데 집중했습니다. 그러나 동아리 프로젝트 특성상 디자인이 계속 변경되었고, 버튼·상단바·하단바처럼 유사한 UI와 상태 관리 코드가 여러 파일에 중복되어 있었습니다. 디자인이 바뀔 때마다 같은 코드를 반복 수정해야 했으며, 일부 화면의 수정을 놓칠 가능성도 커졌습니다.

개선 행동

  • 반복되는 버튼, 상단바, 하단바를 공통 컴포넌트로 분리
  • 화면별로 달라지는 데이터와 스타일을 Props로 주입하도록 구조 개선
  • 반복되는 상태 관리 로직을 별도로 분리
  • 프론트엔드에서 필요한 데이터 전달 방식에 관한 가이드라인을 백엔드 팀에 제안

결과 및 배운 점

리팩터링 이후 디자인 변경 시 수정해야 하는 파일이 줄어 변경 사항을 더 빠르고 일관되게 반영할 수 있었습니다. 프론트엔드 개발의 품질은 화면을 빠르게 구현하는 데서 끝나는 것이 아니라, 팀원이 이해하고 변경하기 쉬우며 지속적으로 확장할 수 있는 구조에서 결정된다는 점을 배웠습니다.

목표와 역할

3개월 안에 실제 사용자가 테스트할 수 있는 수준으로 담당 기능을 완성하는 것을 목표로 했습니다. 물품 대여와 운영 일정의 사용자·운영자 페이지, 카카오·네이버 소셜 로그인 연동을 담당했으며, 프론트엔드 개발자에게 전달받은 HTML을 JSP와 전자정부표준프레임워크 환경에 맞게 연결했습니다.

문제와 해결 과정

적은 인원으로 시민이 실제 이용할 공공서비스를 개발해야 했기 때문에, 제한된 기간 안에 담당 기능을 빠짐없이 완성해야 했습니다. 전체 개발 범위를 기능별로 구분하고 마감 기한을 역산해 매일 완료할 목표를 정했습니다. 개별 화면 구현에만 집중하지 않고, 사용자의 신청이 운영자 화면에 전달되고 운영자의 변경 사항이 다시 사용자 화면에 반영되는 전체 업무 흐름을 기준으로 기능을 점검했습니다.

결과 및 배운 점

담당 기능을 3개월 안에 테스트 가능한 수준으로 완성했고, 서비스는 계획대로 출시되어 현재도 운영 중입니다. 높은 목표일수록 해야 할 일을 구체적인 실행 단위로 나누고 매일 책임 있게 완수해야 한다는 점, 그리고 사용자 화면뿐 아니라 운영자가 서비스를 관리하는 과정까지 체계적으로 설계해야 안정적인 서비스가 완성된다는 점을 배웠습니다.

문제와 해결 과정

한 번에 수천 건의 정보를 수집하는 Python 크롤러를 어떤 방식으로 주기 실행할지 고민했습니다. 크롤링 작업이 Spring Boot API 서버와 자원을 공유하면 서비스 응답과 운영 안정성에 영향을 줄 수 있다고 판단해, 크롤링 로직을 별도의 Python 스크립트로 분리하고 Docker Compose로 실행 환경을 구성한 뒤 EC2의 crontab을 통해 정해진 시간마다 실행되도록 구현했습니다.

처음으로 AWS EC2에 서비스를 배포하면서 자동 배포, 컨테이너 실행, Linux 명령어, HTTPS 적용 과정에서 여러 문제를 경험했습니다. 문제 원인을 하나씩 확인하며 GitHub Actions 기반 배포와 Nginx·Certbot 설정을 끝까지 완성했습니다.

배운 점

  • 작업의 특성과 서비스에 미칠 영향을 고려해 실행 방식을 선택하는 문제 해결력
  • API 서버와 배치성 작업을 분리해 운영 안정성을 고려하는 관점
  • AWS, Docker, Linux, CI/CD를 활용해 개발 결과물을 실제 서비스 환경에서 운영하는 역량
  • Refresh Token의 개념과 필요성에 대한 이해
